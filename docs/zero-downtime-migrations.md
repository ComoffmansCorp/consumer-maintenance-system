# Миграции без даунтайма

Эта система использует `golang-migrate` (см. `migrations/`, `make migrate-up`/`make migrate-down`,
и CI-джоб `.github/workflows/ci.yml`, который прогоняет весь каталог миграций против чистой БД
на каждый пуш). Все текущие миграции (`000001_init`, `000002_add_images`) безопасны для
применения на живой системе без остановки трафика — они только добавляют таблицы/колонки,
ничего не удаляют и не переименовывают. Ниже — методология на случай миграций, которые
потенциально ломают совместимость (переименование/удаление колонки, смена типа, добавление
`NOT NULL` без дефолта), чтобы деплой оставался безопасным и при росте схемы.

## Почему обычный "одна миграция = один деплой" ломается

Golang-приложение — скомпилированный бинарник: старый код (`app` до раскатки нового образа) и
новая миграция БД не могут появиться одновременно чисто. При `docker compose up --build -d app`
или в реальном rolling-деплое какое-то время существуют **и старые, и новые** экземпляры кода,
обращающиеся к **одной и той же** базе. Если миграция удаляет или переименовывает колонку, старый
код тут же начинает падать на каждом запросе к ней — то самое "работало на стейдже, упало в
проде между деплоем миграции и деплоем кода".

## Паттерн expand/contract (расширение → сокращение)

Любое потенциально ломающее изменение схемы разбивается на **минимум три отдельных деплоя**,
каждый безопасен сам по себе:

1. **Expand** — миграция добавляет новое (колонку/таблицу), ничего не удаляет. Старый код её
   просто не видит и продолжает работать как раньше.
2. **Migrate & dual-write** — деплой кода, который пишет **в оба места** (старое и новое поле) и
   бэкофилл существующих строк (одноразовый скрипт или `UPDATE ... WHERE new_col IS NULL`
   пачками, чтобы не держать лок на всю таблицу). Читает пока ещё из старого поля.
3. **Cutover** — деплой кода, который читает и пишет только новое поле. Старое поле полностью
   не используется.
4. **Contract** — только теперь отдельная миграция реально удаляет старую колонку. К этому
   моменту гарантированно ни один работающий инстанс кода на неё не ссылается.

Конкретный пример из этого проекта: если бы понадобилось переименовать
`master_profiles.avatar_url` → `master_profiles.photo_url`, ломающий вариант — одна миграция
`RENAME COLUMN`. Безопасный: (1) добавить `photo_url`, (2) задеплоить код, пишущий в оба поля +
разовый бэкофилл, (3) переключить чтение на `photo_url`, (4) отдельной миграцией дропнуть
`avatar_url`.

## Что уже безопасно "из коробки" в этом проекте

- **Добавление nullable-колонки** (как `000002_add_images`) — безопасно всегда, старый код её
  просто не знает.
- **Добавление новой таблицы** — безопасно всегда.
- **Добавление индекса** — использовать `CREATE INDEX CONCURRENTLY` в проде (не в транзакции
  миграции — `golang-migrate` по умолчанию оборачивает каждый файл в транзакцию;
  `CONCURRENTLY` требует явного отключения через `-- +migrate NoTransaction` или отдельный
  небуферизованный запуск), иначе `CREATE INDEX` держит блокировку на запись на всё время
  построения индекса.
- **`ALTER TABLE ... ADD COLUMN ... NOT NULL` без дефолта** — НЕ безопасно на большой таблице:
  Postgres до версии 11 требовал полный rewrite таблицы под блокировкой; начиная с PG 11+
  (у нас `postgres:16`) добавление `NOT NULL DEFAULT <const>` быстрое (не требует rewrite), но
  сам факт `NOT NULL` без дефолта на существующих строках всё равно упадёт с ошибкой, если
  таблица не пуста — значит либо дефолт, либо двухшаговая миграция (добавить nullable → бэкофилл
  → `SET NOT NULL` отдельной миграцией после того, как все строки заполнены).

## Порядок деплоя

Общее правило: **миграция БД — вперёд кода, откат кода — раньше отката миграции**.
Expand-миграция безопасна раньше кода, который её использует (старый код её просто не видит);
contract-миграция — только после того, как весь старый код, ссылавшийся на удаляемое поле,
гарантированно выведен из эксплуатации (все реплики передеплоены на новую версию).
