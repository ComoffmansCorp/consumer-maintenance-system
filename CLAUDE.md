# CLAUDE.md — Consumer Maintenance System (backend + admin)

> Положи этот файл в корень репозитория `consumer-maintenance-system` под именем `CLAUDE.md`.
> Это постоянные правила проекта. Следуй им во всех задачах. Если задача
> противоречит правилам — останови работу и спроси.

## 1. Что это за проект
Production-grade система выездного обслуживания приборов учёта (счётчиков).
Пользователи: диспетчер/администратор (веб-админка) и инспектор (мобильное
приложение, отдельный репозиторий). Бэкенд переписывается с Java Spring Boot
на Go. Цель — не CRUD, а зрелая система с интегрируемым API.

Домены: auth (пользователи, роли), organization, address, meter (счётчики),
task (наряды + жизненный цикл), act (акты осмотра и замены), photo
(фотофиксация), notification (вынесенный сервис).

## 2. Технологический стек (не менять без согласования)
- Go (последняя стабильная версия)
- Роутер: chi
- БД: PostgreSQL, драйвер pgx
- Доступ к данным: sqlc (типобезопасный SQL). НЕ использовать GORM/ORM
- Миграции: golang-migrate. НИКОГДА не использовать ddl-auto/create-drop
- Аутентификация: golang-jwt (access + refresh)
- Логи: slog (структурные)
- Метрики: Prometheus; трассировка: OpenTelemetry
- PDF: библиотека генерации PDF на Go (см. раздел 7)
- Админка: Vue 3 + Vite + TypeScript + Pinia + Tailwind CSS + Axios
- Инфра: Docker, docker-compose, GitHub Actions

## 3. Архитектура — СТРОГИЕ ПРАВИЛА
Модульный монолит, спроектированный под выделение микросервисов
(ports & adapters поверх доменных модулей).

Структура:
```
cmd/api/main.go            # composition root, связывает порты с реализациями
internal/<domain>/         # auth, organization, address, meter, task, act, photo, notification
  handler.go               # HTTP-слой
  service.go               # бизнес-логика
  repository.go            # доступ ТОЛЬКО к таблицам своего домена
  ports.go                 # интерфейсы, нужные домену от соседей
  dto.go                   # контрактные структуры на границе
  models.go                # внутренние модели (наружу не торчат)
internal/platform/         # auth, db, broker, middleware, observability, config
internal/server/router.go
migrations/
```

Правила границ (нарушать нельзя):
- Слои внутри домена: handler → service → repository. Слои не перепрыгивать.
- repository домена обращается ТОЛЬКО к таблицам своего домена. Никаких
  cross-domain JOINّов. Нужны чужие данные — через порт (интерфейс) соседа.
- Домены зависят от интерфейсов (ports.go), не от чужих реализаций.
- На границах домены обмениваются DTO, не внутренними моделями.
- Кросс-доменные эффекты — через события в брокер, где допустима отложенная
  согласованность (напр. «задача выполнена» → уведомление).
- Связывание реализаций с портами — только в composition root (cmd/api/main.go).

## 4. Конвенции Go
- Ошибки оборачивать (`fmt.Errorf("...: %w", err)`), не игнорировать.
- Никаких panic в обработчиках; паники наружу не выпускать.
- context.Context первым аргументом во всех вызовах с I/O; таймауты обязательны.
- Транзакции на операциях, меняющих несколько таблиц.
- Валидация входных данных на границе (handler), до бизнес-логики.
- Конфигурация только через env (см. раздел 6). Хардкод запрещён.
- Имена: пакеты — по домену, без `utils`/`helpers`-свалок.
- gofmt + golangci-lint должны проходить. Запускай линтер перед завершением задачи.

## 5. Конвенции фронтенда (Vue)
- Vue 3 Composition API + `<script setup lang="ts">`. Только TypeScript.
- Состояние — Pinia (по доменам: authStore, taskStore, ...).
- HTTP — Axios через единый api-клиент с перехватчиком JWT и refresh.
- Структура: views/ (страницы), components/ (переиспользуемые), stores/, api/, types/.
- Никакой бизнес-логики в компонентах — только отображение и вызовы stores.
- Все списки — с пагинацией и состояниями loading / empty / error.

## 6. ДИЗАЙН-СИСТЕМА (единая для веба и Android)
Дизайн-язык: «Приборная точность» (Field Precision). Серьёзный технический
инструмент для энергетики — точный, надёжный, без игрушечности. Смелость
тратится в одном месте (моноширинные технические данные + статусы-индикаторы),
всё остальное — тихое и дисциплинированное.

### Палитра (CSS-переменные / Tailwind config)
- ink `#0F172A` — основной текст, тёмные поверхности
- graphite `#1E293B`
- slate `#475569` — вторичный текст
- mist `#94A3B8` — третичный/подписи
- line `#E2E8F0` — границы (hairline)
- surface `#F8FAFC` — фон
- white `#FFFFFF` — карточки
- **primary `#0D9488`** (refined teal) — основные действия, акцент. Один акцент, с restraint.
- Семантика статусов: created=slate `#64748B`, assigned=blue `#2563EB`,
  in_progress=amber `#D97706`, completed=green `#059669`, canceled=red `#DC2626`.
Тёмная тема обязательна (ink-фон, инвертированная шкала).

### Типографика
- Display/заголовки: «Space Grotesk» — геометрический гротеск, с restraint.
- Body/UI: «Inter».
- **Data/mono: «JetBrains Mono»** — для технических данных: показания счётчиков,
  серийные номера, ID/UUID, координаты, временные метки. Это signature-элемент.
- Чёткая типошкала; data всегда mono, табличные цифры (`tabular-nums`).

### Компоненты и правила
- Hairline-границы (1px line), радиус 8px, щедрые отступы, без тяжёлых теней.
- Статусы — компактные чипы-индикаторы (как приборные индикаторы), цвет из семантики.
- Таблицы данных — плотные, но воздушные; mono для технических колонок.
- Состояния пустоты — приглашение к действию, не «нет данных».
- Ошибки — что случилось и как починить, голосом интерфейса, без извинений.
- Кнопки называются действием («Назначить», «Сформировать акт»), и тост после
  повторяет действие («Акт сформирован»).
- Quality floor без объявления: адаптивность до мобильного, видимый focus,
  respect `prefers-reduced-motion`. Анимации сдержанные и осмысленные.
- Копирайтинг: со стороны пользователя, активный залог, sentence case, без воды.

## 7. Генерация PDF (акты осмотра и замены)
- Акт — юридический документ: формируется из данных акта строго по шаблону.
- Содержимое: реквизиты организации, адрес, данные счётчика (серийник,
  показания — mono), дата, ФИО инспектора, прикреплённые фото, место под подпись.
- Генерация на стороне Go, выдача как `application/pdf`.
- Шаблон выносить отдельно; данные подставлять, не хардкодить.
- PDF должен быть детерминированным и корректно отображать кириллицу (шрифт с
  поддержкой кириллицы встроить).

## 8. БЕЗОПАСНОСТЬ — НЕ ОБСУЖДАЕТСЯ
- Секреты ТОЛЬКО в env / secret manager. НИКОГДА не коммить секреты, ключи,
  пароли, JWT_SECRET. Если видишь секрет в коде/README — вынеси в env и сообщи.
- Пароли — argon2 или bcrypt. Никакого хранения в открытом виде.
- Все SQL — параметризованные (sqlc/pgx это обеспечивают). Никакой конкатенации.
- JWT: проверка подписи, короткий access + refresh.
- RBAC и изоляция тенанта — в middleware на сервере, не на клиенте. Каждый
  запрос ограничен tenant_id текущего пользователя.
- Загрузка фото: проверять тип, размер, санитизировать имя файла.
- Rate limiting и явный CORS.

## 9. Production-готовность (Definition of Done для задач)
Задача не «готова», пока не выполнено применимое:
- Версионируемая миграция (если менялась схема).
- Юнит-тесты ключевой логики + интеграционные с testcontainers.
- Структурные логи с request-id; метрики на новые эндпоинты.
- Health/readiness не сломаны; graceful shutdown сохранён.
- Эндпоинты задокументированы в OpenAPI; формат ошибок — problem+json.
- Идемпотентность на небезопасных операциях (Idempotency-Key).
- golangci-lint и тесты зелёные в CI.

## 10. Команды
- `make run` / `docker compose up` — запуск
- `make test` — тесты
- `make lint` — линтер
- `make migrate-up` / `migrate-down` — миграции
(Если цели отсутствуют — создать в Makefile.)

## 11. Чего НЕ делать
- Не использовать ORM, не возвращаться к create-drop.
- Не делать cross-domain JOIN'ы и прямые обращения к чужим таблицам.
- Не коммитить секреты.
- Не плодить `utils`/`common`-свалки.
- Не добавлять технологии «для веса» без обоснования предметной областью.
- Не заявлять «прошло промышленную эксплуатацию» — только «готово к интеграции».
- Не оставлять списки без пагинации и состояний loading/empty/error.
